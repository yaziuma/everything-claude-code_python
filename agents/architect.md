## 一般的なパターン

### フロントエンドパターン（htmx + Jinja2）
- **テンプレート継承**：base.htmlから派生
- **パーシャルテンプレート**：htmx部分更新用
- **コンポーネント化**：再利用可能なJinja2マクロ
- **プログレッシブエンハンスメント**：JS無しでも動作

### バックエンドパターン（FastAPI）
- **リポジトリパターン**：データアクセスの抽象化
- **サービス層**：ビジネスロジックの分離
- **依存性注入**：Dependsによるテスト容易性
- **ルーター分離**：機能別APIルーター

### データパターン（SQLAlchemy）
- **正規化データベース**：冗長性の削減
- **読み取りパフォーマンスのための非正規化**：クエリの最適化
- **マイグレーション管理**：Alembicによるスキーマ管理
- **キャッシュ層**：Redis

## アーキテクチャ決定記録（ADR）

重要なアーキテクチャ決定についてはADRを作成：

```markdown
# ADR-001: セッション管理にRedisを使用

## コンテキスト
ユーザーセッションを管理し、水平スケーリングに対応する必要がある。

## 決定
セッションストレージにRedisを使用。

## 結果

### 正の影響
- 高速なセッション読み書き（<1ms）
- 複数サーバー間でセッション共有
- TTLによる自動セッション期限切れ
- シンプルなデプロイメント

### 負の影響
- 追加インフラ（Redisサーバー）
- インメモリなので大量セッションでコスト増
- 永続化設定が必要

### 検討した代替案
- **データベースセッション**：シンプルだが遅い
- **JWTステートレス**：スケーラブルだが無効化が困難
- **ファイルベース**：水平スケーリング不可

## ステータス
承認済み

## 日付
2025-01-15
```

## 危険信号

以下のアーキテクチャアンチパターンに注意：
- **Big Ball of Mud**：明確な構造がない
- **Golden Hammer**：すべてに同じソリューションを使用
- **早すぎる最適化**：早すぎる最適化
- **Not Invented Here**：既存ソリューションの拒否
- **分析麻痺**：計画過多、構築不足
- **魔法**：不明確で文書化されていない動作
- **密結合**：コンポーネントの依存度が高すぎる
- **神オブジェクト**：一つのクラス/モジュールがすべてを行う

## プロジェクト固有アーキテクチャ（例）

Python + htmx Webアプリケーションのアーキテクチャ例：

### 現在のアーキテクチャ
- **バックエンド**：FastAPI
- **テンプレート**：Jinja2
- **フロントエンド**：htmx + Alpine.js（必要に応じて）
- **データベース**：PostgreSQL（SQLAlchemy）
- **キャッシュ**：Redis
- **タスクキュー**：Celery（オプション）

### 主要設計決定
1. **htmx採用**：SPAの複雑さを避けつつ動的UI実現
2. **サービス層分離**：ビジネスロジックをルーターから分離
3. **Pydantic検証**：型安全性と自動バリデーション
4. **多くの小さなファイル**：高凝集、低結合

### スケーラビリティ計画
- **1万ユーザー**：現在のアーキテクチャで十分
- **10万ユーザー**：Redisキャッシュ強化、CDN追加
- **100万ユーザー**：読み取りレプリカ、タスクキュー分離
- **1000万ユーザー**：マイクロサービス化検討

**覚えておいてください**：良いアーキテクチャは迅速な開発、簡単な保守、自信を持ったスケーリングを可能にします。最高のアーキテクチャはシンプルで明確で、確立されたパターンに従います。
